# Deployment

DataSentry ships as **one Docker image** that serves both the API and the built web app. It needs PostgreSQL 14 or
later. This guide covers two ways to run it:

- Locally with Docker Compose, which was tested end to end.
- On free hosting, with exact manual steps. This setup has **not** been deployed or verified by the authors.

## 1. Local: Docker Compose

```bash
cp .env.example .env
# Edit .env and set SECRET_KEY and POSTGRES_PASSWORD. These commands generate values:
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
python3 -c "import secrets; print(secrets.token_hex(16))"

docker compose up -d --build --wait
open http://localhost:8000            # or visit it in a browser
```

Compose starts four services:

- `db`: PostgreSQL 16.
- `migrate`: runs `alembic upgrade head` once.
- `api`: the API and web app on port 8000. Set `API_PORT` to change the port.
- `worker`: the job scheduler.

Uploaded files go in the `storage` volume and the database in the `pgdata` volume.

**Optional: an admin account and synthetic sample data.**

```bash
SEED_ADMIN_PASSWORD='choose-a-long-password' \
  docker compose --profile seed run --rm seed --email you@example.com --scenarios all
```

If you leave out `SEED_ADMIN_PASSWORD`, a random password is generated and printed once.

**Check the deployment:**

```bash
python3 scripts/e2e_scenario.py --api http://localhost:8000
```

This creates its own expiring demo workspace and checks the following:

- the health endpoint and the error format
- a healthy control batch
- that a defect opens an incident
- that unapproved remediation is refused
- that quarantine resolves the incident only after verification

**What was verified for this release.** With `ENVIRONMENT=production`:

- The compose stack started.
- Migrations applied.
- `/api/v1/ready` reported ready.
- The scenario script passed.
- The Playwright browser tests passed against the container.
- The seed command ran.
- The API refused to start with the development `SECRET_KEY`.

## 2. Free hosting: Render (app) + Neon (database)

> **Not verified.** The steps below follow the providers' documentation as of October 2026. Nobody has run them for
> this release, so check the result yourself with `scripts/e2e_scenario.py` before you call it deployed.

### Why this combination

- **Render free web services run Docker images.** They also have the following limits:
  - They spin down after 15 minutes without traffic and take about a minute to wake.
  - They have 512 MB of RAM and 0.1 CPU.
  - Their filesystem is ephemeral, so `STORAGE_BACKEND=database` keeps uploads in Postgres.
  - They cannot run background workers or cron jobs.
  - Outbound SMTP is blocked, so leave the SMTP settings empty.
- **Render's free Postgres** expires 30 days after creation and is deleted after a 14-day grace period. A separate
  free database is a better fit.
- **Neon's free plan** does not expire. It gives you 1 GB of storage per project, scales compute to zero after
  5 minutes idle, and includes 100 compute-unit hours per project each month.

Sources: [Render free instances](https://render.com/docs/free), [Neon pricing](https://neon.com/pricing). Limits
change, so check both pages before you rely on these numbers.

### Steps

1. **Push this repository to GitHub.**

2. **Create the database on Neon.**
   1. Sign up at [neon.com](https://neon.com).
   2. Create a project, choosing a region close to your Render region.
   3. Copy the **connection string**. It looks like
      `postgresql://USER:PASSWORD@ep-xxx.REGION.aws.neon.tech/neondb?sslmode=require`.

   DataSentry accepts `postgres://` and `postgresql://` URLs and adds the psycopg driver itself.

3. **Create the web service on Render.**
   1. In the Render dashboard, choose **New → Blueprint** and select the repository. Render reads `render.yaml`.
   2. When prompted, set `DATABASE_URL` to the Neon connection string.
   3. Set `CORS_ORIGINS` to your service URL, for example `https://datasentry-xxxx.onrender.com`. The app is served
      from the same origin, so this only matters for other browser clients.
   4. `SECRET_KEY` and `CRON_SECRET` are generated by Render.
   5. Apply the Blueprint. The first build compiles the web app and installs the Python dependencies.

   On every start, the container runs `alembic upgrade head` because `RUN_MIGRATIONS=true`.

4. **Check the deployment** from your machine:

   ```bash
   curl https://YOUR-SERVICE.onrender.com/api/v1/ready
   python3 scripts/e2e_scenario.py --api https://YOUR-SERVICE.onrender.com
   ```

   The first request after an idle period can take about a minute while the service wakes.

5. **Run scheduled jobs.** Free Render services cannot run a worker, so the Blueprint sets
   `SCHEDULER_MODE=external`. To have GitHub Actions call the run-due endpoint every 15 minutes:
   1. In the Render dashboard, copy the generated `CRON_SECRET`.
   2. In the GitHub repository, go to **Settings → Secrets and variables → Actions** and add:
      - `DATASENTRY_URL`, set to `https://YOUR-SERVICE.onrender.com`
      - `DATASENTRY_CRON_SECRET`, set to the same value as `CRON_SECRET`
   3. The `Scheduled jobs` workflow (`.github/workflows/scheduled-jobs.yml`) starts working once both secrets
      exist. Each call also runs maintenance, which purges expired demo workspaces and old predictions.

   Note that every call wakes the service, which uses free instance hours. GitHub may also delay or skip scheduled
   runs.

6. **Optional: create an admin account.** Free Render services have no shell. Run the seed command from your own
   machine against the Neon database instead:

   ```bash
   cd backend && pip install -e .
   DATABASE_URL='postgresql://…neon…' SECRET_KEY='the-render-secret' STORAGE_BACKEND=database \
   SEED_ADMIN_PASSWORD='choose-a-long-password' python -m app.seed --email you@example.com
   ```

   Use the same `SECRET_KEY` as the service so the API keys you create stay valid. Alternatively, register through
   the UI. Registration is open while `ALLOW_REGISTRATION=true`.

### Expectations and limits on free hosting

- **Memory.** In local Docker, the API used about 225 MB after seeding a demo workspace. That is under the 512 MB
  limit, but large uploads raise peak memory. The Blueprint caps uploads at 10 MB.
- **Speed.** Seeding a demo workspace took about 9 s locally, on 4 vCPUs. At 0.1 CPU it will be much slower. This
  hasn't been measured on Render.
- **Database size.** Uploads stored in Postgres count toward Neon's storage limit. `MAX_DEMO_WORKSPACES` limits how
  many demo workspaces can exist at once, and demo workspaces expire after 24 hours.
- **Rate limits** are kept in memory per instance. That works with one free instance.

## 3. Other hosts

Any host that runs a container and passes environment variables will work. Set these:

| Variable | Notes |
|---|---|
| `ENVIRONMENT=production` | Turns on the startup safety checks. |
| `SECRET_KEY` | A random value of at least 32 characters. Changing it invalidates sessions and API keys. |
| `DATABASE_URL` | PostgreSQL connection string. |
| `RUN_MIGRATIONS=true` | Or run `alembic upgrade head` as a release step. |
| `STORAGE_BACKEND` / `STORAGE_DIR` | Use `local` with a persistent volume mounted at `STORAGE_DIR`, or use `database`. |
| `SCHEDULER_MODE` | `embedded` for a single always-on instance, `worker` plus a separate `python -m app.worker` process, or `external` with a cron calling `POST /api/v1/jobs/run-due`. |
| `TRUSTED_PROXY_HOPS` | The number of proxies in front of the app, usually 1, so that rate limits apply per client. |
| `PORT` | The listening port. The default is 8000. |

To build the image by itself:

```bash
docker build -t datasentry .
docker run -p 8000:8000 --env-file .env -e RUN_MIGRATIONS=true datasentry
```

To build the web app for a different API origin, use `--build-arg VITE_API_URL=https://api.example.com` and add the
web origin to `CORS_ORIGINS`.

## Upgrades and backups

- Migrations are forward-only Alembic revisions. Take a database backup before you upgrade: Neon offers branching
  and point-in-time restore, and elsewhere you can use `pg_dump`.
- `SECRET_KEY` signs sessions and keys API-key hashes. Rotating it signs everyone out and invalidates all API keys.
